
================================================================================
                    再保管理系統 - 需求分析文件生成指令
                              v1.0
================================================================================

【目的】
本指令用於指導任何AI模型（如ChatGPT、Claude、Gemini等）根據HTML原型和需求資訊，
生成標準的需求分析文件（Word格式）。

【適用功能】
- 再保管理系統的任何新功能模組
- 合約管理、報表分析、審核流程等任何需求分析
- 生成格式統一的需求文檔

================================================================================
【第一部分】文檔結構
================================================================================

## 文檔整體框架

```
Page 1:  封面頁
         - 大標題：再保管理系統
         - 副標題：X.X.X [功能名稱]
         - 需求分析文件 v1.0
         - 基本信息表（功能模組、編制日期、文件編號、狀態）

Page 2:  版本歷史
         - 版本號 | 發佈日期 | 主要變更 | 負責人

Page 3:  目錄
         - 1. 執行摘要
         - 2. 需求目的與業務背景
         - 3. 業務需求說明
         - 4. 功能需求（4.1欄位定義、4.2按鈕操作邏輯）
         - 5. 與外部系統整合
         - 6. API 規範
         - 7. 附錄

Pages 4+: 詳細內容（見第二部分）
```

## 1. 執行摘要

### 1.1 專案概述
- 簡述功能在整個系統中的位置
- 說明功能涵蓋的核心業務流程
- 範例：「本功能為『再保管理系統』中的『合約基本資訊管理』。該功能涵蓋
  再保合約的新增、查詢、編輯、版本管理等核心業務流程，為保險合約管理
  提供完整的資訊化解決方案。」

### 1.2 業務價值
使用「• [價值項]：[具體說明]」的格式列出4項主要價值：
- 提升效率
- 確保完整性
- 支持控制
- 便利管理

### 1.3 成功標準
使用「✓」符號列出5-7項可衡量的成功標準


## 2. 需求目的與業務背景

### 2.1 業務背景
- 列出該功能解決的5項主要痛點
- 使用「• 」符號
- 範例：「• 合約資訊分散，管理效率低下」

### 2.2 需求目的
- 列出5項核心目的
- 格式：「[目的]：[具體描述]」
- 範例：「統一管理：建立統一的合約資訊管理平台」

### 2.3 主要使用者
- 建立3-4行的表格
- 列：使用者角色 | 職能描述 | 主要操作
- 範例角色：合約管理員、簽核人員、業務人員


## 3. 業務需求說明

### 3.1 業務流程
- 列出5-6項核心流程
- 格式：「【流程名稱】：[步驟描述]」
- 範例：「【新建合約】：使用者點擊『新增合約』按鈕 → 開啟表單 → 填寫資訊...」

### 3.2 核心業務規則
- 列出8-10項核心規則
- 使用編號列表（1. 2. 3. ...）
- 包含：編號規則、狀態流轉、權限限制等


## 4. 功能需求

### 4.1 欄位定義

#### 4.1.1 查詢區域欄位
建立表格：序號 | 欄位名稱 | 類型 | 長度/格式 | 說明
- 通常3-5個查詢欄位

#### 4.1.2 主要表單欄位
建立表格：序號 | 欄位名稱 | 英文名 | 類型 | 必填 | 驗證規則 | 說明
- 通常10-15個欄位
- 關鍵欄位：ID(系統產生)、名稱、類型、日期、狀態、險別等

### 4.2 按鈕操作邏輯

每個按鈕需包含：

#### [按鈕N] [按鈕名稱]
**觸發條件：** [如何觸發]

**處理邏輯：**
1. [邏輯步驟1]
2. [邏輯步驟2]
3. [邏輯步驟3]
...

**驗證規則：**
✓ [驗證規則1]
✓ [驗證規則2]
...

【常見按鈕】
- 新增、編輯、刪除
- 查詢、重置、匯出
- 查看、版本、簽核
- 續期、保存


## 5. 與外部系統整合

### 5.1 整合概述
簡述需要整合的外部系統

### 5.2 整合清單
表格：序號 | 整合系統 | 整合內容 | 整合方式

常見外部系統：
- 使用者認證系統(SSO/LDAP)
- 審批流程系統(Workflow)
- 電子簽章系統(E-Signature)
- 日誌審計系統(Audit Log)

### 5.3 詳細整合說明
對每個外部系統：

#### 5.3.X [系統名稱]整合
【整合目的】[簡述目的]
【整合方式】[方式說明]


## 6. API 規範

### 6.1 API概述
- 說明使用RESTful API
- 列出標準（HTTPS、JSON、認證方式等）
- 參考共用規範文件

### 6.2 本功能的主要API列表
表格：API名稱 | 方法 | API路徑

常見API：
- GET /api/v1/[資源] - 查詢列表
- GET /api/v1/[資源]/{id} - 查詢詳情
- POST /api/v1/[資源] - 建立
- PUT /api/v1/[資源]/{id} - 更新
- DELETE /api/v1/[資源]/{id} - 刪除


## 7. 附錄

### 7.1 狀態流轉圖
- 簡潔文字：「[狀態1] → [狀態2] → [狀態3] → ...」
- 狀態說明表（新）：序號 | 狀態 | 說明
- 操作說明表（新）：狀態 | 可執行的操作
- 關鍵規則（用加粗標題和文字說明）

### 7.2 代碼說明
表格：代碼 | 名稱 | 說明
（如險別代碼、狀態代碼等）

### 7.3 術語表
- 格式：「[術語]：[定義]」

### 7.4 實施假設與約束
- 列出6-8項核心假設
- 格式：「• [假設項]：[具體說明]」

### 7.5 API詳細規格
- 逐一說明每個API的：
  - 請求方法
  - API路徑
  - 必填/可選參數
  - 成功/失敗回應範例

## 如何從HTML原型提取信息

### 步驟1：識別所有表單欄位
- 從<input>、<select>、<textarea>等元素提取
- 提取 id、name、type、placeholder、required等屬性
- 確定欄位名稱、類型、是否必填

### 步驟2：識別所有按鈕
- 從<button>元素提取
- 提取文字、onclick事件、class等
- 確定按鈕名稱、觸發方式

### 步驟3：識別表格結構
- 從<table>元素提取
- 提取表頭、數據行
- 確定要顯示的欄位和資訊

### 步驟4：識別狀態和流程
- 查看表格中是否有狀態欄位（如status）
- 查看表格中是否有操作按鈕顯示
- 推斷狀態流轉邏輯

### 步驟5：推斷業務規則
- 基於表單欄位名稱推斷業務規則
- 基於按鈕操作推斷業務流程
- 基於資料結構推斷系統設計

【範例】
從HTML看到：
- 欄位：contractNo(ID), contractName(名稱), signDate(簽署日期), 
  effectiveDate(生效日期), expireDate(失效日期), insuranceType(險別)
- 按鈕：新增、編輯、刪除、查看、簽核、續期、版本、匯出
- 表格資料：顯示合約列表和狀態

推斷：
- 這是合約管理功能
- 支持CRUD操作
- 有版本管理和簽核流程
- 有狀態管理和續期功能

## Word文檔格式

### 字體和大小
- 正文：11pt 微軟雅黑
- 標題1（章節）：18pt 加粗
- 標題2（子章節）：14pt 加粗
- 標題3（子子章節）：12pt 加粗

### 顏色
- 表格標題背景：#D9E9F7（淡藍）
- 標題文字：#667EEA（藍紫色）
- 重點文字：加粗或著色

### 表格
- 所有表格使用 Light Grid Accent 1 樣式
- 標題行使用背景色和白字
- 內容行保持白色背景和黑字

### 頁面佈局
- 一級標題後添加分頁符
- 表格前後添加段落間距
- 列表項使用項目符號或編號

【第五部分】內容編寫建議
================================================================================

## 語言和風格
- 使用台灣繁體中文（不使用簡體字）
- 使用正式、專業的用語
- 避免口語化表達
- 使用「使用者」不用「用户」
- 使用「欄位」不用「字段」
- 使用「匯出」不用「导出」

## 常用詞彙對照
- 數據 → 資料
- 系统 → 系統
- 字段 → 欄位
- 导出 → 匯出
- 进行 → 進行
- 查询 → 查詢
- 软件 → 軟體
- 验证 → 驗證

## 文檔一致性
- 確保系統名稱統一為「再保管理系統」
- 確保功能模組編號統一（如「1.1.1」）
- 確保表格格式一致
- 確保用語和格式統一

【第六部分】質量檢查清單

在完成文檔前，檢查以下項目：

□ 字體、大小、顏色是否統一
□ 表格格式是否一致

□ 驗證規則是否完整
□ API規範是否準確
□ 是否有分頁符確保格式正確
□ 是否使用了正確的台灣用語
□ 版本歷史表是否有內容
□ 附錄是否完整

## 應用場景1：根據HTML生成合約管理需求文檔

1. 解析HTML中的表單欄位 → 填入4.1章節
2. 解析HTML中的按鈕 → 填入4.2章節
3. 基於HTML推斷業務規則 → 填入3.2章節
4. 基於功能特性撰寫執行摘要 → 填入1章節
5. 根據系統架構設計整合章節 → 填入5章節
6. 根據API標準撰寫API規範 → 填入6章節

## 應用場景2：生成其他功能模組的需求文檔

1. 替換功能模組名稱（如「報表分析」）
2. 替換對應的表單欄位和按鈕
3. 替換對應的業務規則和流程
4. 保持文檔結構和格式不變
5. 生成新的需求分析文檔

【第九部分】常見問題解答】
================================================================================

Q1: 如果HTML中沒有完整的業務邏輯說明怎麼辦？
A: 根據UI設計和字段名稱進行合理的推斷，並在「實施假設與約束」中清楚地說明。

Q2: 需要多少個按鈕操作的詳細說明？
A: 所有用戶交互的按鈕都應該有詳細說明（通常8-12個）。

Q3: API規範應該有多詳細？
A: 包含主要的CRUD操作API即可，詳細規格可參考共用規範文件。

Q4: 表單欄位應該列出多少個？
A: 所有在HTML中出現的欄位都應該列出，包括查詢欄位和表單欄位。

Q5: 如何處理跨系統的功能？
A: 在第5章「與外部系統整合」中詳細說明整合點和方式。
